## 1. 结论与产品定位

Fanto 不应被设计成一个要求用户先分类、先整理、先决定主题的传统笔记工具。它的核心价值是：**先自然留下记录，再由 AI 发现可能的联系，最后让用户决定哪些联系值得继续生长。** 前端应让记录足够轻，让整理的结果可理解、可追溯、可修正，而不是让用户为了使用 AI 而学习新的复杂工作流。

现有 Demo 已清楚表达了这一方向：`记录` 展示按时间排列的原始内容，`脉络` 展示 AI 发现的新建议和已经在生长的长期主题；底部只有两个主导航，右侧提供全局创建入口。脉络页的文案“AI 发现可能的联系，你决定留下什么”应视为重要产品原则，而不仅是装饰性文案。来源：HTML 第 19–31 行。

正式产品的主循环建议确定为：

```text
自然表达 / 附加素材
        ↓
保存原始 Record
        ↓  异步整理，不阻塞保存
AI 发现候选联系或更新已有脉络
        ↓
用户查看依据 → 确认 / 修正 / 暂时略过
        ↓
Topic 持续生长 → 阅读、继续表达、回溯来源
        ↘
         新 Record 再次进入整理循环
```

这张图描述的是目标产品逻辑，不代表 Demo 已实现。尤其要区分：原始记录是用户的事实资产，AI 整理是可修改的解释层，候选建议是尚未被用户确认的关系。任何动画、卡片或文案，都不能让这三层在数据上混淆。

### 1.1 应保留与应调整的部分

| 保留的设计资产 | 正式实现的调整方向 |
|---|---|
| 双主导航“记录 / 脉络” | 不为了功能增加而轻易扩展为五个 Tab；详情、设置等进入次级路由。 |
| 低饱和蓝灰、宽松留白、轻玻璃质感 | 收敛为语义化 Token；提高文字及操作对比度，限制玻璃和阴影使用。 |
| 日期选择 + 轻量时间线 | 保留日历作为时间定位工具，但日期、记录列表和标题必须共享状态。 |
| 图文、语音、地点的混合记录 | 保留多模态承载方式，补全真实附件、播放、详情、失败与权限状态。 |
| “新的可能”叠层卡片 | 保留轻量发现感，取消循环确认逻辑，增加来源、去重和明确的处理结果。 |
| “已经在生长”的两列主题卡 | 保留小型内容卡的节奏；长内容、动态字体和窄屏可切换单列。 |
| 全局浮动创建入口 | 保留快速捕获，但入口应汇聚到统一 Composer，而非分裂成多套记录流程。 |

### 1.2 三条不可破坏的产品原则

**记录先于整理。** 创建成功的判断是原始内容得到可靠保存，而不是 AI 已完成分析。后台整理失败不能让已保存记录消失，也不能要求用户重新输入。

**AI 建议必须有依据。** AI 可以提出关系、标题、摘要和候选归并，但应允许用户查看来源、编辑解释、拒绝或撤销。不能把推测性心理、身体或人格判断包装成事实；例如 Demo 中“身体正在重新喜欢傍晚”是文学化候选标题，而不是可直接断言的健康结论。

**用户拥有最后的整理权。** 跳过不等于删除记录，确认不等于允许修改原文，脉络的合并、归档或修改也不应悄悄破坏来源关系。重要状态变化必须可观察、可恢复。

### 2.3 可访问性与视觉问题

现有 `--accent:#527f91` 与白色的对比度约为 **4.37:1**，在普通文字要求下略低于 4.5:1；`--secondary:#727982` 在背景 `#f8f9fa` 上约为 **4.17:1**，`--tertiary:#a6adb4` 约为 **2.15:1**。这些是按 sRGB 计算的静态值，半透明叠加、实际背景和系统显示仍需分别测试。来源：第 8、9 行。正文中大量 11–12px 的时间、转写及来源信息，在移动端长期阅读时偏小；34px 音频条和 18px 播放按钮的实际可点击区域也不足。第 11–13 行。

日历中的记录点太小且仅依赖颜色；月份标题、星期和选中日期使用不一致的字号与字重；某些无边框图标（⌁、◌、◖、▧、⌖）在不同平台字体中形态不可控。两列 Topic 卡片通过 `nth-child` 分配薄荷绿和浅蓝色，颜色与内容语义无关，容易让用户误以为颜色表达类型或状态。第 10–13 行。建议保留色彩的安静感，但把“可读、可点、可理解”置于纯视觉纤细感之上。

现有 HTML 缺少完备的可访问名称、选中态语义、键盘焦点指示、动态更新公告、弹层焦点管理和完整日期标签。部分 DOM 看似交互控件，实际只是 `span` 或 `article`；正式实现必须按行为选择按钮、链接、导航、对话框和列表等语义，而不能只靠 `onclick`。

## 3. 信息架构与导航

### 3.1 正式产品的信息结构

```text
Fanto
├─ 记录（默认主 Tab）
│  ├─ 日期浏览 / 时间线
│  ├─ Record 详情
│  │  ├─ 原文与附件
│  │  ├─ 音频 / 图片 / 视频 / 链接查看
│  │  └─ 关联脉络（若存在）
│  └─ 统一捕获 Composer（全局入口）
├─ 脉络（第二主 Tab）
│  ├─ 新建议队列
│  │  ├─ 建议详情 / 来源依据
│  │  └─ 确认、修正、加入已有脉络、暂不处理
│  └─ 已有脉络列表
│     └─ Topic 详情
│        ├─ 当前整理内容
│        ├─ 来源记录
│        └─ 继续表达 / 对话（目标能力）
└─ 次级能力（按阶段开放）
   ├─ 搜索
   ├─ 设置 / 主题 / 隐私
   └─ 数据导出及其他管理能力
```

其中 Record 详情、建议详情、Topic 详情、统一 Composer 为真实产品闭环所必需的建议新增页面；原 Demo 并未展示其具体 UI。搜索、导出、复杂任务中心等不应被本文视作已确定的 P0 功能。

### 3.2 导航规则

主 Tab 仅承担最高频的两个目的：“回看我留下的内容”和“理解这些内容正在形成什么”。全局创建入口在两个 Tab 均可访问。详情页属于当前导航分支，不新增底部 Tab。进入详情时可隐藏全局浮动导航，由详情底部的专属操作区取代，避免双层悬浮控件争夺空间。

切换 Tab 保留各自的筛选日期、列表滚动和未提交的界面上下文。再次点击当前 Tab 可以触发回到顶部，但不得触发清空数据。详情返回时恢复原列表位置；关闭 Composer 时若有未保存输入，必须保留草稿或给出明确的放弃确认。iOS 使用系统导航/返回手势，H5 支持浏览器前进后退与深链接；两端不应自造冲突的手势。

### 3.3 路由约定（建议）

H5 可采用 `/records`、`/records/:id`、`/topics`、`/topics/:id`、`/suggestions/:id` 等语义路由。Composer 可由带路由语义的 Sheet/Modal 承载，以便浏览器返回关闭弹层、刷新后合理恢复状态。iOS 使用等价的导航目的地和稳定数据 ID，而不要求与 Web 完全相同的技术实现。路径仅为建议，不代表已有 API。

## 4. 视觉设计系统

### 4.1 设计气质

关键词为：**安静、可信、清晰、轻盈、有生长感。** 背景应让内容自然浮现，而不是通过高饱和装饰制造科技感；白色或低对比表面承担层次，深色文字承担阅读，蓝灰色承担交互重点。装饰性渐变、玻璃、阴影和动画应有明确用途，避免每个元素都像可点击的悬浮卡。

正式产品应采用统一设计 Token，不能把页面中分散的 `#59636c`、`#69727a`、`#587082` 等硬编码继续扩散。颜色应描述用途而不是只描述色相，例如 `text.secondary`、`surface.raised`、`action.primary`、`status.error`、`focus.ring`。主题卡颜色应是可选的低强度装饰，不承担唯一的信息编码。

### 4.2 Light 语义色板（建议起点）

下表为设计候选值，需在真实组件、透明层和设备中复核，并非声称已经完成视觉定稿。

| Token | 建议值 | 用途与约束 |
|---|---|---|
| `canvas` | `#F7F8FA` | 主背景，避免大片强烈渐变。 |
| `surface.primary` | `#FFFFFF` | 日历、卡片、Sheet 主表面。 |
| `surface.subtle` | `#F1F4F6` | 次级分组、输入背景。 |
| `surface.accent` | `#E6F0F3` | 选中/信息强调的浅色表面。 |
| `text.primary` | `#202329` | 标题与正文。 |
| `text.secondary` | `#59636D` | 说明、元信息及次级正文。 |
| `text.muted` | `#626B75` | 较弱但仍需正常阅读的文字；不要用于占位式禁用语义。 |
| `text.disabled` | `#A6ADB4` | 真正不可操作内容；不可承载必要信息。 |
| `action.primary` | `#426B7A` | 主按钮、选中背景、交互文本。 |
| `action.onPrimary` | `#FFFFFF` | 主色上的文字和图标。 |
| `action.subtle` | `#E6F0F3` | 次级选中或轻强调。 |
| `border.subtle` | `#E1E6EA` | 轻分隔，不能作为唯一焦点轮廓。 |
| `border.strong` | `#A9B3BB` | 较强边界，可按实际背景调整。 |
| `status.success` | 语义绿色待校验 | 保存成功、完成状态，不用于普通装饰。 |
| `status.warning` | 语义琥珀色待校验 | 待处理风险、非阻塞问题。 |
| `status.error` | 语义红色待校验 | 失败、危险操作及错误提示。 |
| `focus.ring` | 高对比蓝灰待校验 | 键盘焦点；需与相邻背景达到可辨识要求。 |

主色 `#426B7A` 与白色约为 5.81:1，`#59636D` 与白色约为 6.12:1，`#626B75` 与建议背景约为 5.14:1。数值是设计筛选依据，不可代替对所有实际状态的验收。普通文字目标至少 4.5:1，大号文字至少 3:1，必要的非文字控件及状态边界至少 3:1；具体遵循 WCAG 2.2 AA 的适用条件。

### 4.3 Dark 主题

深色模式不应只是反转颜色，也不应把所有卡片变成浓蓝色。建议采用近中性的深灰背景、略亮一级的表面和适当降低亮度的蓝灰强调色。保留白天的层次关系，减少深色背景上的大面积阴影，以表面明度和细边界建立层级。图片、视频及用户输入内容保持真实色彩，不附加主题滤镜。

建议起点：`canvas #111518`、`surface.primary #1B2226`、`surface.subtle #242D32`、`text.primary #EDF1F3`、`text.secondary #B5C0C6`、`action.primary #A9C4D0`、`action.onPrimary #17313C`。所有浅蓝文字、选中按钮、边框、媒体控制和禁用状态必须重新测量对比度，不能直接复用 Light 透明度。用户可选择“跟随系统 / 浅色 / 深色”，未设置时跟随系统。iOS 可使用平台动态颜色映射，H5 使用相同语义 Token 的 CSS 变量。

### 4.4 字体与排版

使用系统字体族，iOS 优先系统中文与 San Francisco，H5 使用系统 UI 字体栈，不依赖不可控的远程字体下载。中文正文不应整体套用明显负字距，英文数字和短标题可以局部微调。不要为了视觉纤细牺牲读写清晰度。

| 层级 | 建议字号 / 行高 | 用途 |
|---|---|---|
| Display | 32 / 38 | 顶级页面标题，按端及窗口调整。 |
| Title | 24 / 31 | 重要详情标题。 |
| Section | 18 / 26 | 区块标题。 |
| Body | 16 / 25 | 记录、AI 正文、主要可读内容。 |
| Body Small | 14 / 21 | 卡片摘要、辅助说明。 |
| Metadata | 12–13 / 18 | 时间、来源、计数；不再默认用 11px。 |
| Button | 14–16 / 20–24 | 根据操作层级使用。 |

iOS 必须支持 Dynamic Type，Web 应尊重浏览器字体缩放及用户文字设置。字号放大时，容器随内容增长，不能依赖固定高度来“保住设计稿”。日期、金额、时长等建议使用系统国际化格式化能力。农历显示属于本地化增强，不应与公历主日期混淆，且其缺失不能阻碍记录浏览。

### 4.5 间距、形状与材质

建议采用 4px 基础间距体系，常用值为 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40。移动页面水平内容边距以 20px 为起点，窄屏可调整到 16px；卡片内部 16–20px，段落之间 8–12px，主要区块之间 24–32px。通过一致的留白形成节奏，不用任意 margin 修补布局。

圆角建议分为 8（媒体小元素）、12（按钮/输入）、16（普通卡片）、20–24（大卡片/Sheet）、全圆角（日期选中和小型状态胶囊）。不要一个页面混用大量相近但无意义的圆角。普通卡片以细边界或极轻阴影为主；重要浮层可增加柔和阴影。`backdrop-filter` 只用于浮动导航、短暂菜单或少量覆盖层，不能让整页所有卡片都玻璃化。减少透明度设置启用后使用不透明表面。

### 4.6 图标与图片

导航及操作图标采用同一图标体系，统一线宽、视口、视觉重心和填充规则；不再混用 Unicode 符号模拟图标。图标承载实际操作时必须配文字或可访问名称，不能只凭颜色识别状态。图标大小通常 20–24，点击热区由容器提供。用户图片使用真实缩略图，加载失败显示清晰的重试/占位状态；Demo 的渐变色块仅是测试素材，不属于正式内容视觉规范。

## 5. 全局布局与多端适配

### 5.1 移动端基本布局

移动端采用单列内容、可滚动主区域、底部主导航和独立的创建操作。当前 430px 的最大宽度仅适合桌面预览壳，不应变成真实 iPhone 的硬编码上限。iPhone 页面应填满可用宽度，背景延伸到屏幕边缘，内容遵守系统安全区。浮动控件与内容之间必须保留足够滚动底部空间，最后一条记录不能被导航遮挡。

建议默认内容边距 20px，屏幕小于约 360px 或文字放大时可缩至 16px。内容可读宽度、字号和卡片布局应由可用尺寸决定，而不是依赖某个特定手机型号。横屏、分屏、键盘和动态字体需要有明确降级布局；不要把横屏简单裁掉。

### 5.2 iOS、H5 和桌面差异

| 场景 | iOS | 移动 H5 | 桌面 H5 / 大屏 |
|---|---|---|---|
| 主导航 | 系统导航习惯与安全区，保留双主目的。 | 自适应底部导航，支持浏览器历史。 | 可改为侧栏或顶部导航，不模拟狭窄手机壳。 |
| 内容宽度 | 自适应设备宽度。 | 自适应视口。 | 阅读正文建议限制约 680–760px，列表/双栏可更宽。 |
| Topic 列表 | 宽度充足时两列，窄屏及大字可单列。 | 同左，基于容器宽度而非设备型号。 | 可扩展为两至三列，避免卡片过宽。 |
| Composer | 原生 Sheet/编辑页，使用系统键盘和媒体选择器。 | Sheet 或全屏编辑层，适配软键盘。 | 居中对话框或侧边编辑面板。 |
| 媒体 | 系统照片、相机、录音、分享能力。 | 浏览器能力和权限适配；不支持时有回退。 | 文件选择、拖拽粘贴可作为增强。 |
| 返回 | 原生导航返回和系统手势。 | Browser History / Esc / 可见返回。 | 路由、键盘和面包屑（按需要）。 |

这里的约 360、680–760 等尺寸是布局建议断点，不是平台硬性标准。正式组件应优先根据容器空间自适应，而不是只用 `device-width` 媒体查询。

### 5.3 安全区、键盘和悬浮层

底部导航与 FAB 应挂在同一布局系统中，计算安全区、控件高度和内容 padding，而不是分别写死 bottom。H5 使用 `env(safe-area-inset-*)`，并根据浏览器和 WebView 的可见视口处理键盘；动态视口单位可作为布局基础，但不能假设所有 WebView 对软键盘的处理一致。iOS 使用原生 safe area 与键盘避让机制。键盘出现时优先保证输入框和发送按钮可见，必要时隐藏或替换底部主导航，不能把 Composer 挤到键盘下方。

多个 Overlay 必须有统一层级：页面 < 导航 < 临时菜单 < Sheet/详情浮层 < 系统权限/媒体界面 < 必要的提示。不能只靠不断增加 z-index 解决遮挡。菜单打开时关闭或暂停其他冲突浮层；全屏编辑时全局 FAB 不得盖住发送按钮。

## 6. 记录页设计规范

### 6.1 记录页的唯一核心任务

记录页负责忠实呈现用户留下的内容，并让用户快速找到、阅读、继续补充。它不应在用户浏览时主动把原文改写成 AI 摘要，也不应要求用户理解整理算法才可以查看内容。AI 状态可以作为轻量附属信息出现，但不应压过原始记录。

### 6.2 日期与时间线的统一行为

建议首版明确采用 **按日浏览模式**：默认进入今天，按创建时间倒序展示当天记录；用户选择其他日期后，标题、周/月日历和记录查询同步切换。日历作为时间导航，而不是仅用于装饰或改变高亮。用户可以通过上/下一日、日历选择或“查看更早记录”进入其他日期；记录数据始终完整保留，按日视图不意味着只能访问当天记录。未来若引入连续滚动的“全部记录”模式，须作为明确的浏览模式另行设计，不可让一个日期选择同时承担过滤和滚动锚点两种含义。

统一状态至少包括：`selectedDate`（YYYY-MM-DD，本地日期）、`visibleMonth`、`calendarMode`（week/month）、`recordsByDate`、`loading/error` 和各 Tab 的滚动位置。`selectedDate` 不应由日号推导，必须包含完整年月日。日历标记来自日期索引，记录展示来自查询结果；缓存允许，但必须有失效和刷新策略。

选中日期时立即更新视觉选中态和标题，列表进入对应加载状态；成功后显示该日内容，失败时保留日期并显示可重试错误，不能悄悄回到旧日数据。切换日期期间如保留旧内容，必须明确标注正在加载，避免把昨天的记录误认为今天的内容。

### 6.3 周历与月历

周历固定七列，遵循用户选择的周起始日（首版中文地区可默认周一，并保持全局一致）；月历显示完整的 4–6 周网格，可选择是否显示相邻月日期，但样式必须区分清楚。所有日期由同一日历模型生成，周视图和月视图不会分别维护选中状态。切换月/周只改变浏览范围，不自动修改选中日期。

建议：选中日期使用实心主色圆形；今天使用独立的非冲突标识（例如轻描边或“今天”辅助标签）；有记录日期使用小点，且读屏标签说明“有 X 条记录”；今天与选中日期重合时以选中态为主。未来日期可查看但没有未来记录时不应伪装为禁用；若业务规定不能选择未来日期，则应真正禁用并提供语义。月标题必须含年月或可明确识别的年份，跨年不丢失上下文。

日历展开使用内容驱动高度。状态从 collapsed → expanding → expanded 或反向变化；动画中禁止反复触发造成高度错乱，或允许可中断的受控过渡。展开后将焦点留在切换按钮或明确迁移到日历标题，不自动跳到第一周。屏幕阅读器应能读出完整日期、是否选中、是否今天及记录数量。日期点击区域建议至少 44×44 的项目统一目标；在窄屏中如七列无法满足，应优化内边距和整体布局，而不是缩小交互热区。

### 6.4 时间线与 Record 卡片

每条记录建议由时间、正文预览、附件、来源/地点和必要的状态组成。正文一般展示 2–4 行，可根据内容类型调整，但卡片必须能进入完整详情。时间可显示为“18:24”，完整日期在列表日期标题或详情中提供；不必让每条都重复显示到秒。秒级时间保存在数据中，展示时按用户需要格式化。

时间线连接线和节点仅作为视觉辅助，不承担唯一顺序信息。节点颜色不应代表“AI 已整理”而没有文字说明。语音记录应显示清楚的播放、暂停、进度、时长和转写入口；播放按钮的实际热区应足够大，音频未下载或转写失败时仍可访问原音频。图片保持宽高比例的真实缩略图，支持放大及多图浏览；视频展示封面、播放标记和时长；链接展示可验证的标题/域名及缩略信息。没有元信息时不要编造地点、标题或媒体内容。

地点属于可选元数据。默认不要求用户提供定位权限，也不应未经允许把位置写入记录。用户可手动输入或选择地点；真实授权、精度、错误与撤销行为由各端适配。空地点不展示占位行。

### 6.5 Record 详情（新增必需）

详情页完整展示原文、创建/更新时间、附件、可选地点和关联脉络。用户应能查看、编辑自己输入的内容，并能区分原始语音、转写文本与 AI 整理生成的文本。若支持修改原文，应通过明确的编辑操作完成，保存后触发必要的重新整理，而不是在 AI 输出中直接覆盖。

删除、恢复、编辑历史和附件生命周期等需与后端确定契约。建议首版至少提供明确删除确认与可恢复窗口或撤销机制；在服务端未支持前，不应设计出虚假的“已恢复”操作。若记录被关联到多个脉络，删除前应说明关联受到的影响；不能通过删除 Topic 默默删除原始 Record。

### 6.6 空态与异常

当天无记录时显示轻量空态：“这一天还没有记录。”并提供“写一点”和返回今天/选择日期的清晰入口。全局从未记录、某一天为空、加载失败和离线无缓存应是不同状态。列表加载使用与最终布局相近的骨架或简洁进度，不进行无限闪烁。分页加载应保留已成功展示的内容；失败提供局部重试，不能清空整页。

## 7. 统一捕获 Composer

### 7.1 统一入口而不是四种独立产品

Demo 的“写一点 / 说出来 / 放进照片 / 留一个链接”可以保留为快捷入口，但它们应打开同一个 Composer，并根据入口预选键盘、录音、媒体或链接输入方式。用户不应先选择分类、Topic、模板或记录类型。默认直接可以输入一句话；添加素材是附属能力，不是额外的复杂流程。

建议布局为：顶部关闭及草稿状态 → 自适应文本输入区 → 附件预览区域 → 底部附件/录音/发送操作。文字很少时界面应保持轻，输入增长时自然扩展到可滚动编辑区。输入框占位文案建议“想到什么，就记下来。”或同等简短自然表达。发送按钮只有在存在可保存内容且当前状态允许提交时才可用；不要用低对比颜色作为唯一禁用提示。

### 7.2 多模态输入契约

文本、图片、音频、视频和链接不应成为互斥的 Record 类型。建议以“Record + 附件集合”的产品视图管理，一条记录可以有正文和多个素材。语音可保留原始文件并附带用户确认或系统生成的转写；AI 转写不是原音频的替代。链接可以由用户粘贴识别，但应允许直接以纯文本保存，不依赖预览抓取成功。

现有 HTML 不包含真实数据模型或 API，因此不能声称后端已经支持纯附件记录。正式落地需明确 `content`、附件、转写及空内容的保存契约。如果现有后端强制文本非空，而产品允许仅图片或语音，应该调整协议或明确要求用户补充文本，不能由前端虚构正文来绕过校验。

### 7.3 语音、权限与媒体

点击录音前检查平台支持及权限状态，首次授权使用系统提示并提供必要解释。拒绝权限时提供重试或进入系统设置的指导，不循环弹出授权。录音需有明确开始、暂停/继续（若支持）、停止、取消和保存状态；录音中关闭编辑器时必须确认或保留草稿。切换应用到后台、来电中断、设备音频路由变化及录音失败的行为需要真实端测试。

语音转写如为异步能力，原音频保存成功后可继续等待转写；转写失败不得丢失音频。用户应能辨认“原始转写”与“AI 整理内容”。不支持录音的浏览器或 WebView 可以回退至文本/文件上传，不显示不可执行的录音按钮。

### 7.4 保存、草稿与失败

保存状态建议为：`editing → validating → saving → saved`，失败进入 `saveFailed` 并可重试。附件上传可独立经历 `local → uploading → uploaded / failed`。用户点击发送后应立即得到状态反馈，但只有持久化成功才能显示“已保存”。后台 AI 整理应显示为独立状态，不得阻塞记录保存成功。

在网络不佳时可以使用本地草稿和待同步队列，但必须明确“已保存在本机 / 正在同步 / 已同步”的区别；离线本地保存不能被描述为云端已保存。多端同时编辑的冲突、附件上传续传、离线数据清理等应有明确协议。首版至少要保证未保存输入不会因误触关闭、页面切换或普通网络失败而直接丢失。重复点击发送必须通过前端提交锁及服务端幂等保证不产生重复记录。

### 7.5 编辑器关闭与返回

没有修改时直接关闭；有未保存更改时可选择继续编辑、保存草稿或放弃。iOS Sheet 下滑、H5 浏览器返回、Esc 和关闭按钮应进入相同的决策逻辑。记录保存成功后关闭 Composer 并在当前上下文可见地插入或定位新记录；若用户正在浏览历史日期，不应暗中改变筛选导致无法理解新记录去了哪里，可提示“已保存到今天，查看记录”。

## 8. 脉络页与 AI 建议系统

### 8.1 两种对象必须区分

`Suggestion` 是 AI 提出的尚未处理的候选关系；`Topic` 是已经存在、可以持续阅读和更新的长期主题。建议可能指向新 Topic，也可能建议把记录加入已有 Topic，或提出已有 Topic 的合并与修正。Demo 当前以“确认这个脉络”处理所有情况，但正式产品不应把所有 AI 发现都默认变成一个新的 Topic。

一个重要问题是 Demo 同时出现“家里的植物”已存在 Topic 和“家里的植物，很慢地变化”新建议。第 26、28 行。这说明真实产品需要去重、关联已有主题和候选类型判断，而不是简单追加同名卡片。

### 8.2 新建议卡片

建议卡应清楚包含：候选类型、标题、简短解释、来源数量、可查看的依据、主要操作。避免大段 AI 自我表述，让用户一眼看出“它发现了什么，依据是什么，我可以做什么”。来源数量和时间范围必须真实，不应由模型自由生成数值。示例中的“5 条记录 · 3 种输入”应由已验证的关联数据计算。

标题可以有温度，但不得过度拟人化用户或推断健康与心理事实。对于可能涉及健康、人格或敏感生活信息的候选，应使用更审慎的表述，并能看到原始依据。用户可编辑候选标题或描述，而不是只能接受 AI 的命名。

### 8.3 建议处理行为（推荐契约）

“换一条”仅改变当前浏览项，不应隐式代表拒绝或永久跳过。建议提供“暂不处理”或“稍后再看”，并在来源详情或更多操作中提供“不相关/不再建议此关系”。主要按钮随候选类型变化：新建类为“确认并创建”，关联类为“加入此脉络”，合并类应先进入更谨慎的确认详情，不能一键直接合并已有内容。

用户确认前可以查看来源、修改标题、选择加入已有脉络。若新建议与已有 Topic 相似，应优先展示现有候选，避免制造大量重复主题。确认成功后更新相关 Record-Topic 关系和 Topic 列表，移出待处理队列，并提供可撤销或可修正入口。若请求失败，建议仍保持待处理状态并显示重试，而不是先消失后再偷偷恢复。

### 8.4 卡片队列与动画

建议队列由稳定 ID 数组维护，当前浏览项由 `activeSuggestionId` 表示，不使用固定长度的 DOM 数组充当业务数据。状态区分：`ready`、`browsing`、`submitting`、`transitioning`、`empty`、`error`。零张建议显示完成空态，一张建议不进行无意义轮换，两张或更多才展示叠层预览。所有点击在合法状态下才执行。

浏览下一张时，最上层轻微向左退出，后方卡片平缓前移；但不应让用户误认为被丢弃。确认成功可以用更轻的收起/淡出和列表更新表达“已归入脉络”，不必使用相同的丢弃式动画。动画前先确定业务结果，再播放结果对应的视觉过渡。提交中禁用重复确认；动画结束、取消、减少动态、页面卸载均需要有完成或清理路径，不能让 `rotating` 永久为 true。

建议将叠层预览限制为最多三层视觉呈现，但业务队列可以有任意数量。所有卡片通过稳定 key 复用；已确认项不参与下一轮。长文字必须有详情入口，叠层高度适应内容，不能让正文覆盖底部来源栏。减少动态时不使用横向甩出、旋转或明显缩放，而以简短淡入/瞬时替换完成同样状态变化。

### 8.5 已有脉络列表

卡片展示 Topic 名称、简短描述、来源记录数量以及可选的最近更新时间。是否显示状态“生长中/暂停/完成/归档”需先统一业务定义；这些状态不是 Demo 已实现的能力。列表排序建议以最近内容活动为主，用户手动固定/排序可作为后续增强。计数必须由数据计算，不能写死或在每次确认时加一而不处理去重。

两列瀑布式布局适合短内容、宽度充足的手机，但不能保证所有字体与语言下都合理。建议使用容器响应式 Grid：窄屏、Dynamic Type 放大或长内容时单列；常规手机两列；桌面可增加列数并限定卡片最大宽度。卡片背景以统一表面为主，少量淡色可作为可选装饰，但不让 `nth-child` 决定业务含义。用户应能进入完整 Topic 详情，不在卡片上堆叠过多按钮。

### 8.6 Topic 详情（新增必需）

Topic 详情是产品价值真正产生的位置，而不是只展示一张被确认的标题卡。建议最小信息层级为：标题与简短定位、当前整理内容、相关原始记录、继续表达入口。整理内容应清晰区分“用户原始表达”和“AI 归纳”，并保留来源引用；用户可以修正标题或内容，必要时重新整理。来源记录可进入原始详情，确保追溯链路完整。

如果产品已经规划对话式继续思考，建议在 Topic 底部提供统一的输入框：用户可提问、补充或修正；AI 回复中的重要结论可由用户选择沉淀，而不是每一句聊天都自动覆盖 Topic。对话与后台整理的合并规则、任务、外部研究资料等不在当前 Demo 中，需要后续独立设计，不应在本版擅自扩展成复杂工作台。

## 9. 动效系统与状态驱动实现

### 9.1 动效原则

动效只负责解释变化：元素从哪里来、状态如何改变、操作是否完成。它不能决定业务成功，也不能隐藏加载或代替错误反馈。优先使用平台熟悉的导航、Sheet 和控件动效；自定义动效需克制，不做持续漂浮、呼吸、无意义弹跳或大面积模糊变化。

| 场景 | 建议时长 | 形式与注意事项 |
|---|---:|---|
| 按钮按下/释放 | 80–140ms | 轻微颜色或明度变化；主按钮可小幅缩放，不与父级 transform 冲突。 |
| 菜单出现/消失 | 160–220ms | 小幅位移 + 透明度，配合遮罩/焦点管理。 |
| 日历展开/收起 | 200–260ms | 高度或布局过渡，内容稳定，不重置日期。 |
| Tab 切换 | 120–200ms | 轻量过渡或平台默认；保持各自滚动上下文。 |
| 建议浏览 | 220–280ms | 最上层小幅水平退出，后层前移；不循环已处理项。 |
| 确认成功 | 180–240ms | 结果明确后收起/淡出，列表局部更新。 |
| Sheet | 平台默认优先 | 遵循拖动方向与返回手势，不强制统一所有端的曲线。 |
| Toast | 150–200ms | 简短淡入淡出；必要错误不依赖自动消失。 |

以上为设计目标范围，不是所有设备必须严格相同的动画参数。建议共享 easing Token，但原生控件优先使用系统动效。不要统一给所有元素使用 `cubic-bezier(.77,0,.175,1)` 造成过强的加速感。可使用标准 ease-out 或经过设计验证的柔和曲线。

### 9.2 业务状态与动画状态分离

建议操作流程遵循：用户意图 → 校验 → 业务命令 → 确认结果/错误 → 更新数据状态 → 对应视觉过渡。允许针对可安全回滚的操作进行乐观更新，但必须有失败回滚与状态提示。不得依赖动画结束回调才把已确认数据写入模型，也不能因为动画被取消而丢失业务成功结果。

卡片浏览可以独立于业务请求；如果业务请求正在提交，浏览/确认按钮需按状态禁止冲突操作。组件卸载、切换 Tab、减少动态设置变化以及动画取消必须清理事件监听、定时器和动画资源。异步回调需核验当前组件和请求标识，防止过期请求覆盖新状态。

### 9.3 减少动态与低性能设备

响应 iOS Reduce Motion、H5 `prefers-reduced-motion` 等平台设置，所有 CSS、Web Animations API 和原生自定义动画必须共享策略。减少动态时使用瞬时状态替换或简单淡入，不保留大位移、旋转、缩放和持续视差。不能只覆盖 CSS transition 却遗漏 JavaScript 动画。低性能时减少阴影、模糊和动画层数量；尽量让动画作用于 transform/opacity，避免连续强制布局与昂贵滤镜。动画永远不应成为完成操作的唯一途径。

## 10. 交互组件与反馈规范

### 10.1 按钮与触控区域

项目统一采用不小于 44×44pt（iOS）或 44×44 CSS px（Web）的主要触控热区目标，视觉图标可以小于热区。这个值是 Fanto 的统一设计目标，不应误写成所有平台的强制最小标准。相邻控件应有适当间距，避免误触；在受限场景下按平台无障碍标准评估例外。普通可读文本不能因为“高级感”而被缩成难以阅读的浅灰色。

主按钮用于当前页面唯一主要任务，次按钮用于非破坏性辅助动作，危险动作使用独立语义。禁用状态应有可解释原因；请求中显示进度且防重复；操作成功和失败的反馈必须不同。所有自定义按钮有可见焦点、键盘触发和读屏名称。

### 10.2 浮动菜单与 Overlay

FAB 打开时设置正确的展开语义，菜单具有清晰的操作名称。点击外部、Esc、系统返回或选择操作均可关闭；关闭后恢复焦点。若以弹出菜单实现，不能让视觉不可见的按钮继续进入 Tab 顺序。菜单项过多时改用 Sheet 或统一 Composer 的附件工具栏，避免右下角堆叠四五个悬浮气泡遮挡内容。

### 10.3 提示、错误与反馈

Toast 适合“已复制”“已保存”等短暂、非关键反馈；需要用户处理的网络错误、权限失败和数据冲突应使用内联错误、持久 Banner 或明确对话框。多个 Toast 应顺序或替换管理，旧计时器不能关闭新提示。成功反馈不应出现于请求尚未确认时；离线本地保存与服务端同步成功必须使用不同文案。状态变化应提供适当的读屏公告，但避免频繁播报无关加载。

### 10.4 手势与可替代操作

不要将左滑、长按、拖拽作为唯一完成方式。所有重要功能必须有可见按钮或更多菜单等替代入口。删除、归档、拒绝建议等不能与普通浏览滑动混淆。手势阈值、点击与滑动冲突由统一手势处理逻辑管理，避免卡片横滑时触发页面返回或日历切换。

## 11. 前端状态与数据契约

### 11.1 统一领域对象（建议抽象）

以下为前端需要的概念模型，不是现有数据库结构。具体字段及接口需与后端确认。

```text
Record
  id, content, createdAt, updatedAt
  attachments[], optionalLocation, organizationStatus
  linkedTopicIds[]

Attachment
  id, kind, local/remote URI, uploadStatus
  metadata (duration, dimensions, mimeType, etc.)
  optionalTranscript

Suggestion
  id, type, title, description, sourceRecordIds[]
  optionalTargetTopicId, status, version

Topic
  id, title, description, status
  sourceRecordIds[], updatedAt, optionalSummary
```

附件、转写、来源、位置及数据版本都必须与实际协议对齐。前端不应信任模型自由生成的来源数量或用户可见 ID；展示统计应基于可信关系数据。Record 与 Topic 的关系需要明确是否允许多对多、关联数量上限、取消关联和删除级联行为，不能由前端自行猜测。

### 11.2 建议状态机

```text
pending ── accept ──→ accepting ── success ──→ accepted
   │                         └─ error ──→ pending + error
   ├── postpone ─────────────────────────→ postponed
   └── reject ──→ rejecting ── success ──→ rejected

浏览下一张：仅改变 activeSuggestionId，不改变以上业务状态。
```

`postponed` 的重新出现时间、`rejected` 的再推荐策略及撤销窗口需要产品与后端共同定义。若 MVP 不支持这些持久状态，界面应只提供已实现的操作，不可让按钮承诺无法兑现的行为。`accept` 必须携带稳定建议 ID、版本/目标和幂等标识，并由服务端处理重复提交及冲突。成功后返回真实 Topic 与关系结果，前端按结果更新缓存。

### 11.3 数据状态与视图状态分层

建议把服务端数据缓存、领域状态、页面局部状态、短暂 UI 状态分开。服务端数据包括 Records、Topics、Suggestions 及日期索引；领域状态包括创建/确认/拒绝等命令；页面状态包括选中日期、当前建议、列表滚动；短暂状态包括菜单是否打开、动画中、Toast 和焦点。不要让 DOM class 名称或元素顺序成为唯一业务状态来源。

同一个实体在多个页面出现时应共享稳定 ID 与缓存更新策略。确认建议后，建议队列、Topic 列表、Record 关联及计数要保持一致；后台整理完成后应以明确的增量事件或重新查询更新数据，不能让旧请求覆盖新版本。需要防止在两个设备同时确认、同时编辑时产生重复或覆盖。

### 11.4 异步整理的前端可见状态

用户只需要知道记录是否保存、是否有整理结果，以及必要时发生了什么错误，不需要被内部 Agent 执行步骤打断。建议状态文案为“已保存”“正在整理”“已整理”或“整理暂时未完成，可稍后重试”，具体是否展示取决于业务价值。后台长期运行不应在每条记录上持续展示加载旋转。AI 生成内容需要来源、时间和必要的更新状态；用户正在编辑时，不应直接用后台新内容覆盖编辑器。

## 12. 多端工程落地建议

### 12.1 共享什么，不共享什么

建议共享产品领域契约、设计 Token、文案、日期规则、状态机、校验逻辑、埋点语义和 API 协议，而不是强制所有端使用完全相同的 DOM 或视觉实现。iOS 可以采用 SwiftUI 的原生组件与导航体系；H5 可采用 React + TypeScript 等成熟前端栈。技术选型须结合现有代码仓库、团队能力与原生能力需求确认，本文不要求重写已有工程。

```text
产品规则 / 领域契约 / 设计 Token
                │
        共享状态与 API 协议
          ┌─────┴─────┐
          │           │
     iOS 表现层    H5 表现层
     SwiftUI 等    React/TS 等
          │           │
    系统能力适配    Web 能力适配
          └─────┬─────┘
                │
        Record / Topic 服务
```

媒体、录音、图片选择、文件缓存、权限、系统分享、键盘、通知和安全区由平台适配层实现。UI 组件不直接依赖某个设备的原始屏幕尺寸，也不直接处理未经抽象的原生权限返回值。共享领域逻辑可降低多端状态不一致风险，但不应为复用而牺牲平台自然交互。

### 12.2 建议组件结构

基础层包括 TokenProvider、Typography、Button、Icon、Surface、Divider、Skeleton、Toast/Notice、Sheet、OverlayHost。业务组件包括 Calendar、DateSummary、RecordCard、AttachmentPreview、AudioPlayer、TopicCard、SuggestionCard、Composer、SourceRecordList 等。页面层只负责组合和业务事件，不直接写死颜色或复杂动画。每个组件应有可控属性、交互事件、loading/empty/error/disabled 状态和无障碍契约。

### 12.3 H5 特别注意

使用语义 HTML、路由与浏览器历史、响应式布局、可见焦点和系统字体缩放。需要支持 Safari、Chrome 及目标 WebView 的实际版本；媒体录制、文件选择、自动播放、剪贴板和权限需按支持情况适配。不要假设网页在普通浏览器与 App 内 WebView 的安全区、键盘、返回或音频会话行为完全相同。服务端渲染、离线缓存、PWA 等是可选架构能力，不是为了一个 MVP 必须全部引入。

### 12.4 iOS 特别注意

优先遵循系统导航、Sheet、键盘、动态字体、VoiceOver、Reduce Motion 和安全区习惯。保留品牌色与内容风格，但不应强行把 H5 的所有按钮圆角、模糊层和动画复制成原生控件。若采用系统材料或导航栏外观，应随目标 iOS 版本使用合适 API，并进行真实设备验证。原生图片/相机/麦克风权限应符合平台要求；未授权、受限和取消都要有独立结果。应用切后台、系统中断和媒体生命周期应由平台层管理。

### 12.5 数据可靠性与安全边界

用户输入内容应按普通文本安全渲染；AI Markdown、外部链接和附件元数据需要可信渲染/清理与安全链接处理，不能直接拼接不可信 HTML。源 Demo 中 `insertAdjacentHTML` 拼接标题只适合静态演示，真实数据必须避免这种不安全的渲染方式。附件上传须考虑格式、大小、网络失败和服务端校验，不在前端假设文件一定安全。敏感内容、录音及位置权限遵循最小必要原则，避免日志、埋点和错误上报泄露原始记录正文。

## 13. 无障碍、国际化与主题验收

正式产品以 WCAG 2.2 AA 作为 Web 无障碍目标，原生端遵循 Apple 相关 Human Interface Guidelines 和平台辅助功能。文字对比、控件边界、焦点、点击目标、键盘路径、读屏语义、动态字体与减少动态应在设计和组件阶段处理，而不是上线前补丁。完整的日历、浮层、音频播放器和编辑器尤其需要专项测试。

日期必须使用完整年月日与时区语义；列表日期与创建时间格式由用户区域设置决定。默认简体中文可以采用熟悉的“周一 / 9月”等展示，但不能把星期、农历或特定日期写死。多语言文本会改变长度，所有标题、按钮和卡片需允许换行或合理省略，并保留完整内容入口。深色、高对比、减少透明度及文字放大都应保持相同功能，不因视觉设置丢失操作。

参考标准：W3C《WCAG 2.2》；Apple《Human Interface Guidelines — Accessibility / Layout / Motion》。其中 WCAG 对普通文字 4.5:1、大号文字 3:1、必要非文字对比 3:1 及目标尺寸等均有明确适用条件。Apple 对控件尺寸、减少动态、平台安全区和动态文字提供平台化指导；Fanto 统一采用的 44 热区是项目目标，不应与各标准的所有最低要求混为一谈。

## 14. P0 / P1 实施优先级

### P0：让 Demo 成为可信的最小产品

| 工作包 | 最小交付与验收 |
|---|---|
| 设计系统 | Light/Dark 语义 Token、排版、间距、圆角、按钮、图标、Overlay；主要文字和控件完成对比度核验。 |
| 导航与布局 | 双 Tab、独立滚动恢复、详情返回、统一安全区与键盘避让、窄屏/大字布局。 |
| 日期与时间线 | 真实年月日、周/月切换、统一选日、真实记录点、按日查询、加载/空态/错误、完整记录详情。 |
| 捕获闭环 | 统一 Composer、文本与已支持附件输入、草稿、真实保存、失败重试、重复提交保护；录音能力按已确定 MVP 范围落地。 |
| 建议闭环 | 稳定 ID 队列、来源详情、确认/必要修正、去重及加入已有 Topic 的合理路径、真实计数、成功移出队列、失败不丢失。 |
| Topic 基础 | 真实列表及详情、来源记录回溯、标题/整理内容阅读；是否开放对话须与后端能力一致。 |
| 状态与动效 | 所有关键操作有状态机；修复动画锁、定时器、减少动态、固定高度和遮挡问题。 |
| 可靠性 | 网络失败、离线草稿/同步语义、媒体上传失败、权限拒绝、基础无障碍及必要的日志保护。 |

P0 不要求一次性实现完整 AI 工作台、复杂任务管理、知识图谱或全部多媒体高级编辑。若后端尚不支持某种输入或建议操作，应先确认契约再提供真实入口，而不是留下“演示中”的伪功能。

### P1：在闭环稳定后增强

可逐步增加全局搜索、连续时间线/筛选模式、Topic 排序与固定、完善的归档和恢复、多媒体高级编辑、导出、跨端离线同步优化、复杂建议合并与批量处理、更丰富的对话和研究任务等。P1 的排序应由实际使用数据决定，不应因视觉上容易添加而提前制造复杂度。

## 15. 验收场景与测试矩阵

以下为建议的发布前验收标准，需覆盖真实 API 与目标设备，而不仅是静态截图。

| 场景 | 通过标准 |
|---|---|
| 日期选择 | 选择任意已支持日期，周/月选中态、日期标题、列表数据一致；跨月跨年不丢失状态。 |
| 日历展开 | 展开、收起、切换月份不改变真实选中日期；快速重复操作和字体放大无裁切、错位或永久锁。 |
| 空日期 | 无记录日显示正确空态，不残留上一日内容；可返回今天或继续选日。 |
| 记录详情 | 所有截断文字可完整阅读，图片/音频可访问，来源与原始内容一致。 |
| 创建记录 | 文本保存成功后只生成一条记录；连续点击、网络慢和重试不产生重复。 |
| 附件失败 | 上传失败不导致其他已保存内容丢失，可重试或保留草稿。 |
| 语音权限 | 首次允许、拒绝、取消、录音中断及不支持设备均有明确可恢复路径。 |
| 建议确认 | 确认一次只产生期望关系/Topic，队列移除已处理项，数量与服务端一致。 |
| 建议重复 | 快速连点、切页、双设备重复确认、请求失败重试不产生重复 Topic。 |
| 建议耗尽 | 0/1/2/N 张均正常，最后一张处理后显示完成空态，不循环已接受项。 |
| 长内容 | 长标题、多行正文、超长链接、较大字号不会覆盖来源栏或按钮。 |
| 导航恢复 | Tab 切换与详情返回保持合理滚动/筛选上下文；浏览器返回与 iOS 返回行为一致。 |
| 键盘和安全区 | 输入区、发送按钮、底部导航不被软键盘、Home Indicator 或浏览器工具栏遮挡。 |
| 主题与无障碍 | Light/Dark、减少动态、减少透明度、键盘、VoiceOver/读屏、200% Web 文本缩放及目标 iOS 动态字体均可完成核心流程。 |
| 提示竞争 | 连续触发通知不被旧计时器提前关闭；关键错误可阅读并操作重试。 |
| 数据安全 | 不可信文本/AI Markdown 不执行脚本；日志与埋点不意外包含原始记录正文。 |

建议测试尺寸至少覆盖约 320、375、393、430 CSS px 的移动宽度，以及 768、1024px 及更宽窗口；覆盖小屏 iPhone、当前主流 iPhone、iPad/分屏或等价模拟窗口。实际设备列表按项目支持范围确定，不以固定像素截图代替动态布局验证。浏览器覆盖目标版本 Safari/Chrome 及使用中的 App WebView；原生覆盖目标最低 iOS 与当前主要版本。还应测试弱网、断网恢复、后台切换、系统字号变化、深色切换及减少动态即时切换。

### 15.1 建议的非功能指标

这些是后续需要建立基线并验证的工程目标，不是当前 Demo 已达到的性能数据。首屏优先呈现可用内容，不等待 AI 整理；长时间线采用分页/虚拟化等合适策略，避免全量 DOM 导致滚动卡顿；媒体缩略图按需要加载，不直接加载大图；动画在目标设备上以稳定流畅为目标，性能不足时减少装饰效果。需建立创建成功率、重复提交率、建议确认成功率、错误恢复率、首屏可交互时间和关键页面卡顿等指标，具体阈值由设备与服务端基线决定。

## 16. 设计交付物与后续协作方式

正式进入多端开发前，建议形成一套单一事实源：设计 Token（含 Light/Dark）、组件状态与交互说明、主要页面高保真稿、必要动效原型、信息架构/路由、领域对象与 API 契约、异常与空态清单、无障碍规范及验收用例。每个页面至少提供默认、加载、空态、错误、长内容、深色和大字版本。开发不应只根据一张静态设计图猜测状态变化。

推荐的工作顺序为：先确认本规范中的 P0 产品契约 → 建立 Token 和基础组件 → 实现真实记录保存/详情 → 完成日期与时间线 → 实现建议队列和 Topic 数据闭环 → 补全动效及多端适配 → 进行可访问性和异常验收。现有 Demo 可保留为视觉参考和回归用例，但不宜直接作为正式前端架构继续堆叠全局 DOM 查询与硬编码数据。

### 最终设计判断

Fanto 的高级感不应来自更淡的字、更复杂的卡片堆叠或更多模糊阴影，而应来自清晰的内容层级、稳定的交互反馈、恰当的留白，以及用户始终知道自己的记录被如何保存和整理。**保留现有温和的视觉语言，修复状态与数据不一致的基础问题，把 AI 的发现变成有依据、可修正的长期内容，这才是从 Demo 走向真实多端产品的核心。**
