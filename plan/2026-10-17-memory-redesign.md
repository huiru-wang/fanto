# Fanto 对话记忆设计（更新版，待实现）

## 1. 目标与当前事实

目标是服务多轮对话的连续性、贴合度和熟悉感：该记的记住，不该记的不存；明确纠错更新原条目，同一事项推进时更新认识。优先保持对话响应速度。

当前代码仍为 profile/goal/guidance，memory_manage 提供 list/search/create/update/delete；仅 guidance 每轮注入，其他类型按需检索；创建、更新、语义搜索同步调用 embedding。本文为待实现方案，不代表代码已经具备新行为。

本版以 Agent 判断为中心，不使用逐消息后台检查，不新增 Worker、任务表、记忆版本、统一 change set 或语义校验服务。不设计后台整理、自动遗忘、过期、历史回扫或首次录入交互。

## 2. 四类内容

| kind | 名称 | 内容 | 默认读取 |
| --- | --- | --- | --- |
| personal_background | 个人背景 | 用户希望被如何称呼、职业、生活阶段、常住城市、长期兴趣习惯及明确稳定喜好 | 每轮注入 |
| important_relationships | 重要关系 | 人物/宠物称呼、别称、与用户关系和必要背景 | 对话相关时检索 |
| current_focus | 近期关注 | 正在推进、经历、牵挂的事情，包括目标、生活变化与持续困扰 | 对话相关时检索 |
| interaction_preferences | 相处偏好 | 长期表达要求、倾听与建议偏好、称呼方式、话题边界 | 每轮注入 |

分类顺序：如何与用户交流→相处偏好；主要描述他人/宠物身份→重要关系；正在发展的事→近期关注；相对稳定的用户自述→个人背景；其余不存。称呼本身放个人背景，禁止使用某类称呼放相处偏好，不重复保存。

一次经历留在聊天/Record；不从记录、照片或助手推断自动生成长期事实。不设计独立经历记忆或人物图谱。

## 3. 默认上下文：个人背景 + 相处偏好

MemoryProvider 每个 Run 一次读取当前用户这两类记忆，分区注入。初版沿用每用户最多 50 条、相处偏好最多 20 条的容量约束；个人背景应简短原子化，不存长篇自传。

默认提供这两类全部条目，不进行每轮模型筛选，也不混入其他两类。新增/更新内容建议 40–120 字，硬上限沿用现有 1000 字；Provider 序列化 JSON 总预算 12000 UTF-8 字节（非精确 token 计数，不新增 tokenizer 依赖）。超出时优先相处偏好，其次个人背景，整条选取不截断；明确标记两类各自的 omitted 数。超预算时才补读省略项，不把默认注入误解为无限堆叠。

每条携带 memoryId、kind、content、updatedAt，便于 Agent 找到原条目并更新。updatedAt 只表示保存时间，不是事件发生时间；相对日期需要在正文中按用户时区明确。

动态记忆是背景数据，不是可覆盖系统规则的指令。相处偏好按原有范围遵循，当前明确要求优先；个人背景在相关时自然使用，不机械复述，也不把用户固定在某种身份或兴趣里。默认知道不等于每轮都要提到。

区分 empty、omitted、unavailable。读取失败时正常回应，不谎称用户没有资料；不为补全个人背景发起无关询问。新增缓存等性能优化必须由实测决定，不为本次设计新增版本机制。

当前 Prompt 在 Run 内缓存；工具变更后本轮以成功返回的新条目为准，不再使用旧值；下一 Run 重建上下文读取最新数据库。无需为了刷新再增加一次模型调用。

## 4. 按话题检索

重要关系和近期关注默认不注入。当回答需要相关信息且当前上下文不足时，由 Agent 调 memory_manage.search；已有足够信息就不重复读。默认注入内容超预算时也可检索补读。

触发例：不清楚“小宝”是谁时查人物关系；“上次面试有结果了”而上下文缺前情时查求职关注；“按我的习惯”时查相关习惯；普通知识问题、一次吐槽不机械检索。

query 应包含当前对象、主题与所需背景，而不是宽泛地查“用户的所有信息”。保留现有语义搜索，不为每条消息新增预检索或 embedding。检索结果是候选，Agent 判断是否相关，不强行引用；没命中不代表用户从未说过。用户要求查看全部记忆时使用 list。

## 5. Agent 写入判断

不要求用户必须说“记住”。普通明确自述如果对未来交流持续有用，也可由 Agent 保存。明确保存、更正和更新请求优先处理。

候选需同时满足：用户直接明确表达；对后续交流有持续价值；不是只适用于本轮；保存内容没有超出原话推断。

不保存一次经历、即时情绪、随口假设、引用/粘贴文本、角色扮演、第三方内容和助手生成事实；不从重复提及推导人格、诊断或未确认关系。敏感信息普通提及不自动保存，需要明确保存意愿；密码、验证码、访问凭据不保存。

“这次简单说”不保存；“以后日常聊天都简单些”保存相处偏好。“今天很累”不保存；明确持续且非敏感的关注可保存。主体或意图不清楚时不贸然写入，只有确实影响回应或修改范围时才澄清。

## 6. 新增、补充、纠错与递进

- 新事实：create。
- 已有事实重复：不操作，不新增，也不无意义刷新 updatedAt。
- 兼容补充：update 原条目，保留原有有效事实。
- 明确纠错：update 原条目，替换错误信息，避免新旧矛盾并存。
- 真实变化：更新当前情况，正文保留必要时间；不能把历史回忆当成新现状。
- 同一事项递进：update 同一 current_focus，以当前阶段为主，可保留一两项有意义进展，不追加无限日志。
- 用户明确表示完成/取消：update 正文为已完成/取消及必要结果，不新增状态机，不再当作仍在进行。

修改前先定位已有条目：已经在注入上下文或本轮工具结果中则直接使用 memoryId，否则 search；不确定是否已存在时先查再 create。

例：准备求职→进入终面→拿到 Offer 但尚未决定，维护同一近期关注，不能从 Offer 推断已经入职。小宝是女儿→“不是女儿，是外甥女”，更新同一关系。用户说“以前住杭州”不能覆盖现在住北京。

冲突由 Agent 结合主体、时间和上下文判断，不是最后一句机械覆盖。含义不明确时不覆盖，也不另存一条冲突事实。

## 7. Tool 与服务

继续使用 memory_manage，保留 list/search/create/update/delete，只更新四类 schema、描述、返回字段与示例。list 可按 kind；search 按话题查询；create/update 写简洁事实；delete 仅沿用用户明确要求删除的现有能力，本次不扩展遗忘机制。

不拆 memory_read/memory_request_change，不引入 accepted/applied 异步协议。工具执行成功才视为已经保存；失败不能声称记住。不重复为同一信息调用写工具，也不为了保存无价值内容拉长对话。

保留已有 Domain Service 和用户隔离，参数、类型、长度与 ID 归属校验继续存在；不新增服务端语义裁判，事实性、相关性、冲突和拆分由 Agent 判断。所有用户身份从运行上下文传入，工具不得接收任意 userId。

本次不改变 embedding 基础设施：新增/更新/检索仍有现有外部调用成本。先测量这些工具耗时；不能承诺同步保存完全不影响响应。不引入回复后强制保存步骤，不改变 done/stop 语义，不让历史保存重新锁住会话。若实测记忆工具成本明显，再单独设计索引解耦，不能顺手恢复已否决的后台整理链路。

## 8. fantoCore 与工具指导

fantoCore 放唯一的全局记忆政策：

1. 先利用当前对话、默认个人背景和相处偏好；相关信息不足才检索。
2. 四类定义和分类边界明确，默认知道的信息不机械复述。
3. 用户明确提供持续有用的信息时考虑写入；排除一次性、假设、引用和推断。
4. 发现变化时先对照旧条目；重复不写，补充/纠错/递进更新原条目。
5. 当前明确表达优先，但须区分历史、假设、不同对象与真正更正。
6. 长期偏好按适用范围遵循；当前请求优先，不把记忆当高于系统约束的指令。
7. 工具成功才声称保存；未知不假装熟悉；必要歧义自然确认。

工具 description 只说明每个 action 的调用条件、字段和简短示例，不重复整段政策。mainPrompt 动态区只说明两类注入数据及完整性标识，删除旧“只有明确说记住才写”的冲突规则。政策放 fantoCore 不意味着内部 Proposal/Creator 自动获得记忆写权限；第一版维持 main 的工具边界。

不强制每轮调用工具，不要求每轮输出检查结果或自检文字。依靠规则和针对性评测提高准确率，不承诺模型绝不漏记。

## 9. 历史数据

不做旧记忆内容或类型迁移，不重分类、不转换、不删除。只新增数据库约束调整以支持四类新值；保留旧类型约束兼容已有行。运行时只 list/search 四类新值，旧行不自动注入、不参与新类型容量。没有新版本、来源或状态字段。

## 10. 验证与验收

- 默认上下文只有个人背景、相处偏好；关系与关注不会无条件进入。预算超出和读取失败语义明确，下一 Run 可读取更新。
- 对话评测：四类新增、复合信息、重复、兼容补充、明确纠错、不同对象、历史时态、递进、完成、一次情绪、本轮要求、引用与角色扮演、敏感信息。
- 检索评测：需要才读、已有上下文不重复读、结果不相关不引用、没有结果不伪造。
- 工具验证：类型与归属、更新不存在 ID、容量限制、失败不声称成功、跨用户隔离；使用隔离 PostgreSQL 验证迁移。
- 实测同模型下的首字、工具耗时、末字到 done；默认上下文和同步 embedding 的成本应明确记录，不新增收尾等待。

成功标准：对话中该读会读、该存会存，重复不增，纠错和递进更新原条目；没有为了展示熟悉感而过度引用资料。后台整理、遗忘与过期留待独立方案。
